## should
1. **A repaint made from an older active version is treated as a child of the newest version, so a mark/strip carries across a version it was not derived from** · server/src/services/chat/analysisStore.ts:58-70 (`lineage`), barShift.ts:42. Repaint writes no `basedOn` (only scoreVersion.ts:109 does), so lineage falls back to the previous version in the layer by creation time; repaintJobs.ts:14-21 repaints the layer's *active* version. Scenario: v1 -> v2 (CUT, bars move) -> user makes v1 active in the Editor -> repaint -> v3 (derived from v1). Lineage says v3's parent is v2 and `task_type === 'repaint'` gives `{moved:false}`. A mark on v2 is "carried" to v3 (markStale/resolveRange) and the strip shows v2's reading dimmed and clickable as v3's, but v2's bars after the cut are not v3's. A stale mark is sent as fact. Fix: write `basedOn: <source version id>` in repaint (and other task) params, or read `basedOn` first and treat a repaint with none as `UNKNOWN`.
2. **A seconds-only (or analysis-less) mark carried across a SET TEMPO keeps its old seconds** · server/src/services/score/planReferent.ts:`retimed` (returns `mark.seconds` when no bars or no bar times), client chatMark.ts `markStale` (retimed only if `view.shown.versionId === view.versionId`). barShift calls SET_TEMPO "keeps every bar" and says seconds are re-timed when the new reading lands, but the turn right after an APPLY runs before the analysis (FIFO: the turn was queued first, or the analysis has not run). Scenario: hatched strip, mark 0:30-0:45 by time on v2, APPLY SET TEMPO -> v3 at a faster tempo, SEND: the mark pins on v3 as 0:30-0:45 (different music), time-only, and the turn answers about the wrong seconds. With bars the plan is right but the "bars 5-8, 0:10-0:20" line carries v2's seconds (markBlock `where`, since `!analysis` keeps bars). Fix: when the new version's bar times are not read, carry only a bars mark and send no seconds line for it, or treat a seconds-only mark as stale across any `KEEPS` op that can retime (SET_TEMPO).
